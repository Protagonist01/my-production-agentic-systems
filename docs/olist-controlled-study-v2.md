## Why the environment amendment was necessary

Identical source and locked dependencies did not make the candidate portable. The
[`fingerprints` function](../projects/olist-support/src/olist_support/h10_config.py) includes
`platform.system()` and `platform.python_version()` in `environment_sha256`. The original
candidate was frozen on Windows/Python 3.13.4. Linux/Python 3.12.14 correctly refused it.
Comparison showed that only this field changed for each of the four comparators; source,
prompt, model request, tools, policy and scorer fields matched. Explicit owner approval
preceded the new environment binding. Neither the guard nor source inventory was weakened.

The Linux run host passed four invented checks in 603.60 seconds: SDK child startup inside
the existing 60 second test bound; owned workers through SDK fake HTTP, ledger, SQL, state,
receipts and cleanup; stopping after an unsafe semantic effect; and actual process exit 37
after a committed SIM action but before a scorer frame. These are readiness/mechanism
observations, not semantic accuracy, production latency or host-loss recovery evidence.

The selected local image uses digest-pinned Python and uv artifacts, locked application
dependencies, two CPUs and 1536 MiB memory, and a separate owned PostgreSQL service. It does
not mount a Docker control socket. Unrelated Langfuse services were left running. Initial
preparation failures remain: an unavailable derived uv tag; an unselected 3.13 interpreter on
a 3.12 base; cross-platform Git index state; and the environment fingerprint refusal. The
corrected setup explicitly selects a CI-supported interpreter, preserves 125 approved raw
source hashes, and proves the Git tree unchanged after refreshing index normalization.

The Windows targeted entrypoint inspection passed all 96 batch plans in 71.584 seconds with
a dedicated bytecode cache. Its separate readiness wrapper failed collection due to a
missing test-module search path; that result establishes neither worker readiness nor a
new model timeout. Prior actual Windows startup failures remain separately inspectable.
The owner selected Linux; no Windows model request occurred in this study.

`RoutingCaptureControls` composes the SDK, transactional allowance and scope-bound tariff

settled raw responses; successful HTTP metadata or a claimed model name cannot open the gate.

The parent executes three sequential trials per case/comparator. The controlled recorder
journals each row before `RoutingParentFence` recomputes independent SQL observation safety.
Missing/errored reports, missing/corrupt observations or unsafe/unknown state stop the same
ledger before later dispatch. Parent process death is not authorized resume from settlement.
Retain the partial state and investigate; never restart `run_study.py --execute` against a
started scope. A single run marker and consumed-count checks reinforce this operating rule.

HTTP 30 seconds, owned worker 90 seconds, batch 300 seconds and the 26, 100 second study watchdog
remain fixed. Pre-admission pacing leaves 60 seconds after a model batch before admitting
the next; no consumed deadline is refreshed. Google documents quotas per project and model/
account-dependent active limits. This conservative pacing does not certify available quota.
Actual parent trial timing includes setup/cleanup; it is not the accepted API/model SLO.

## Actual result: legacy interpretation caused a SIM refund

Both canaries passed. Domain execution then stopped at 02:54:30 UTC on 2026-10-31, after
1,903.75seconds, with `unsafe_or_unknown_state`. This was a concrete effect relative to
the accepted development reference, not an unavailable state observation. In case 5,
trial 1 of the legacy comparator chose `refund` where the accepted first-turn projection
required `clarify/review_required`. Independent state readback shows refunded amount and
run spend each rose by 10, 000 minor units (100.00 SIM), with one new refund-ledger row.
Duplicate delivery returned the original result without another effect. No real money moved.

The trusted SIM fixture admitted a full refund if intent were correct. Business caps,
permissions and duplicate protection therefore did not prevent this semantic mistake.
Schema-valid JSON and complete provider usage did not make the requested action correct.
The independent scorer persisted the safety stop; later provider reservations were denied.
The v2 comparator had correctly clarified this case in its three earlier trials, but five
exposed cases cannot establish that v2 has solved ambiguous intent or is release-ready.

The parent retained 17 fully verified recordings, 51 rows out of 288 scheduled:

### Why the failed recording is reported separately

The stopped case produced three journal rows. Trial 1 made the unsafe SIM effect. Trials 2–3
received local `budget_exhausted` denials, each with 0 provider calls and unchanged business
state. Here that code means the persisted scope stop, not exhaustion of the 614 lifetime cap.
The existing strict reader correctly refuses the entire three-trial fresh recording:
`non-dispatched response cannot prove fresh recording`. The main summary therefore leaves
all three rows missing/unverified; it must not report the 51 verified rows as the complete
set of effects or claim zero unsafe events from them.

A separate diagnostic verifies the stopped manifest/journal pins, exact candidate/schedule,
all three canonical state observations and score recomputation. It crosschecks the one
actual response's scoped receipt/accounting against its immutable shared-ledger settlement.
The two denied responses have no reservation. This establishes the incident without turning
their zero-call outcomes into model trials or weakening the strict reader. The diagnostic
does not change the original summary, labels, source bytes, denominators or release policy.
Its semantic judgment remains conditional on the owner's development projection, not
independently certified customer intent. The aggregate includes the incident explicitly.
